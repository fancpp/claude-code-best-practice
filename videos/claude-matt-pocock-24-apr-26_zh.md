### LLM 的约束：智能区 vs 愚蠢区

首先，我想谈谈 LLM 具有的那种奇怪的约束，这些奇怪的约束是我们很多工作必须围绕的基础。有个叫 Dex Hy 的家伙，经营着一家叫 Human Layer 的公司，他提出了这个想法：当你使用 LLM 时，它们有一个智能区和一个愚蠢区。当你刚开始使用 LLM 时，比如你刚开启一个新的对话，你从零开始。这时 LLM 会做它最好的工作，因为在这种情况下注意力关系是最不紧张的。

每次你向 LLM 添加一个 token，就像是在向足球联赛添加一支球队。想想每次你向足球联赛添加一支球队时，比赛数量会增加多少。它是二次方增长的。这是因为注意力关系基本上从每个 token 到其他 token，基于位置和单个 token 的含义。这意味着大约在 40% 左右，或者我会说大约 100k 是我新的标记点——因为不管你用的是 100 万上下文窗口还是 200k，情况都一样。它开始变得越来越蠢。所以当你不断向同一个上下文窗口添加东西时，它会越来越蠢，直到做出相当愚蠢的决定。有这种感觉的请举手。是的。酷。

所以这意味着我们希望将任务的大小控制在智能区范围内，对吧？我们不希望 AI 贪多嚼不烂。这又回到了老的建议，比如 Martin Fowler 在《重构》中提到的，或者《程序员修炼之道》也谈到过。不要贪多嚼不烂。保持任务小而精，这样你作为一个开发者，一个人，就不会慌乱，不会进入愚蠢区。

### 多阶段计划和 Ralph Wiggum 循环

但是如何应对大任务呢？如何把一个像——我不知道——克隆一个公司或者做点疯狂的事情这样的大任务，分解成小任务，让它们都能适应智能区？一种方法当然可以是——可能 AI 公司希望你做的或者自然的方式就是继续、继续、再继续。你最终进入愚蠢区，每次请求花掉大量 token。然后你 compact（压缩）回来。我们一会儿再谈正确的 compact 方式。然后你继续、继续、再继续，compact 回来，继续、继续、再继续。我认为这效果不太好，因为沉淀物越来越多——我们一会儿会谈到这个。

所以这里的理论是——这是我一段时间以来一直在做的——我会使用这种多阶段计划：好的，我们这里有一个大任务，分解成小部分，这样我们就可以分块处理，在智能区内完成每一小块工作。以前使用过多阶段计划的请举手。是的，很常见的做法，对吧？这是我们一直以来的做法。当然，在去年十二月之前，我自己也一直是这么做的。

任何有点水平的开发者看到这个都会说："这是一个循环，对吧？这是一个循环。我们有阶段一、阶段二、阶段三、阶段四。为什么不直接用阶段 n？阶段 n 就是我们有一个在后台运行的计划，然后我们在上面循环，直到完成。"这就是——听说过 Ralph Wiggum 作为一种软件实践的吗？好的，酷。没听说过的请举手。实际上，这样更准确。好的。所以有一个叫做 Ralph Wiggum 的想法，本质上就是基于这个——你只需要指定旅程的终点，比如创建一个 PRD（产品需求文档）来描述我们要去哪里，然后对 AI 说：做一个小改变，再做一个能让我们更接近目标的小改变。Ralph 是可行的，但我更喜欢多一点结构。所以这就是我们在思考智能区时达到的状态。

LLM 的另一个奇怪的约束是，LLM 有点像《记忆碎片》里的家伙，对吧？它们一直在遗忘。它们不断重置回初始状态。让我调出这个图。我其实应该用幻灯片的，但我就是更喜欢在一个无限的绘图画布上随机滚动。谢谢你，Steve。

嗯，我想让你掌握的另一个概念是：每次与 LLM 的会话都经历相同的阶段。首先，这里是系统提示。这个灰色框是始终在你的上下文中的东西。你希望它尽可能小，因为如果你在这里放了一大堆东西——如果你有 250k tokens，我见过有人放进去——那么你直接就进入愚蠢区了，什么都做不了。所以你需要让它很小。然后你进入一个探索阶段。这个蓝色是编码代理出去探索代码库的阶段。然后你进入实现阶段，然后是测试和确保它能工作的阶段，运行你的反馈循环等等。基于你做过的事情，有这种感觉的请举手。是的。这大概是任何会话的主要基石。

所以我们来看看。我有两个选择：我可以清除然后回到空状态，或者我可以 compact。当我 compact 时，它会把所有对话压缩到一个更小的空间里。在图示中，这看起来就像这样：你把会话中的所有信息，创建成一个历史记录，一个已发生事件的书面记录。开发者们不知道为什么很喜欢 compacting，但我讨厌它。我更喜欢我的 AI 像《记忆碎片》里的家伙，因为这个状态总是一样的。总是一样的。每次你清除，你回到起点。所以如果你能做到这一点，并且你为此优化，那你就处于一个非常好的位置。

所以这就是我希望你思考 LLM 的两件事，我们在处理的两个约束：它们有一个智能区和一个愚蠢区；它们像《记忆碎片》里的家伙。

让我们来看第一个练习。在我做这个的时候，我希望的工作方式是：我会在这里向你们展示我是怎么做的，而我希望你们也在下面动手尝试。刚才那只是一点讲座。现在让我们实际开始编码。

嗯，我们开始吧。我们将从一个对我非常重要的技能开始——grill me 技能。这个技能非常小，非常小巧。它有助于防止我认为使用 AI 时的主要问题之一：错位（misalignment）。

我所反对的隐含想法是 specs-to-code 运动。有人听说过 specs-to-code 运动吗？请举手。它其实不算一个运动，只是有人在说 specs-to-code。嗯，它的意思是：你可以编写程序或构建应用。构建应用的最佳方式是编写一些规格说明，写一个文档，然后把文档变成代码。怎么变？把它交给 AI。如果生成的代码有问题，你不看代码，而是回头改规格，然后再继续。这基本上就是 vibe coding 的另一种说法——你本质上忽视了代码。你不需要担心代码。你只需要不断编辑规格，最终就会到达目标。我试过这个。我真的试过，它很糟糕。它行不通，因为你必须掌控代码。你需要理解代码里有什么。你需要塑造它，因为代码是你的战场。

### 深模块 vs 浅模块

所以在这个最后部分，我要做两件事。首先我要告诉你——你可能在思考这个问题：假设我工作的代码库是一个糟糕的代码库，AI 在里面从来做不好工作，实际上大多数人类进入那个代码库也做不好工作。我如何改进那个代码库？第二件事是，我会展示我的并行化设置。

我们先说糟糕的代码。在哪？图在哪？在这里。在 John Ousterhout 的书《软件设计哲学》中，他谈到了理想的模块类型。想象你有一个看起来这样的代码库。这些块是单个文件。这些文件导出东西。它们有你要从文件中拉取并在其他地方使用的东西。你可能会有奇怪的依赖关系，这个文件可能依赖这个文件，或者依赖那个文件。

如果这些文件很小，而且它们不导出很多东西，John 会称它们为**浅模块（shallow modules）**。它们看起来像——实际上我画不出好图——基本上就是很多小块。这对 AI 来说很难导航，因为它不太理解所有东西之间的依赖关系。它没法搞清楚所有东西在哪里。它必须手动跟踪整个图，然后去"这个依赖这个，这个依赖这个"。

这也很难测试，因为你在哪里画测试边界？你单独测试每个模块吗？然后在这里画个测试边界，再往下一个，再下一个？还是你应该做大组测试？说"好的，我们把这些相关的模块一起测试"，然后希望它们能工作。

这意味着糟糕的测试大多看起来像这样：AI 试图把每个小函数都包在自己的测试边界里，然后测试它们各自独立工作。但这样做的问题是，当这个模块调用那两个模块（它依赖这两个模块）时，这个模块可能会错误地排序函数，或者那个模块内部有一些值得单独测试的东西。如果你再把它包在测试边界里，你怎么办？你 mock 其他两个模块吗？那怎么行？所以实际上，弄清楚如何构建一个易于测试的代码库是至关重要的，因为如果我们的代码库易于测试，我们的反馈循环就会更好，AI 在代码库中的工作也会更好。有道理吗？

那么好的代码库长什么样？不是那样的。是这样的：你拥有 John Ousterhout 所谓的**深模块（deep modules）**。这些模块有一个小的接口暴露出来，暴露出一个简单的小接口，内部有很多功能。这意味着它们很容易测试，因为——假设这个和这个之间有依赖关系。我的箭头？好了。那你只需要在那个模块周围画一个大测试边界。你会捕获很多好东西，因为你测试了很多功能，而调用者有一个简单的接口可以使用。所以不太复杂。有道理。深模块 vs 浅模块。这是好的。浅的版本是坏的。

我发现，如果不加辅助，或者你不仔细监督 AI，它会产生一个看起来像这样的代码库。所以你在指导它时真的需要非常小心。这也是为什么——如果我们看 PRD，PRD 去哪了？在 issues 里面。在游戏化系统里面。嗯，没找到。当然不在。在这里。然后我里面写了数据模型和模块。所以它明确地说：这个游戏化服务是一个新的深模块，我们要围绕它进行测试。它会有这个特定的接口。嗯，我们也在修改进度服务、课程路由、仪表盘路由等等。所以我在规划过程中始终非常具体地指定我正在编辑的模块，并在整个规划和实现过程中牢记模块图。有道理吗？非常非常有用。

### 改进代码库架构技能

### Push vs Pull：编码标准

问题是：我是否应该在早期规划阶段尝试优化计划？这实际上是我看到很多人做的事情，而且这是一个非常好的想法。当我们回到阶段时。假设你有所有这些阶段，你已经和 LLM 搞清楚了所有事情。你理解了你要去哪里。你创建了目的地文档。你接下来应该尝试优化那个 PRD，直到它成为你能想象的最完美的 PRD 吗？我认为这没有太大价值，因为旅程只是对你想要去哪里的一个提示，而你需要投入精力的地方是 QA，你可以 AFK 做这个，但根据我的经验，你不会从中获得很多收益——真正重要的是与 AI 的对齐，你在最初的 grilling 会话中就完成了。

（听众："你如何在你的工作流中让它按你想要的方式编码？这样到了代码审查的时候，它至少熟悉并且使用了你想要的库。"）

是的。我们之前有过这个问题，本质上就是：如何让代理执行你的编码标准？有两种不同的方式。嗯，有**推（push）**和**拉（pull）**。推和拉是什么意思？推就是把指令推给 LLM。你说，好的，如果你在 CLAUDE.md 里放点东西，那个指令总是会发送给代理，对吧？这是一个推送动作。你在推送 token 给它。拉是让代理有机会拉取更多信息。例如 skills。一个 skill 可以放在仓库里，它有一个简短的描述头部说：好的，代理，你需要时可以拉取这个。

我目前关于代码审查和编码标准的思考是这样的。当你有一个实现者——我要把这个红色变得不那么红——嗯，你想要编码标准可以通过拉取获得。如果它有疑问，你想要它能够回答。但如果你之后有一个自动审查者，那么你想要推送。你想要把信息推给审查者。你要说："这些是我们的编码标准。确保这个代码符合它们。"所以如果你有 skills，你想要把那些东西推给审查者，这样审查者既有写好的代码，又有编码标准可以对比。希望这回答了你的问题。我也可以给你展示一个自动化版本。

### Sand Castle：并行 AFK 循环

实际上，嗯，是的，我们就趁热打铁。我最近花了大概一周左右的时间构建了一个叫 **Sand Castle** 的东西。我有点不满意市面上那些用来 AFK 运行代理的选项。它本质上是一个 TypeScript 库，用于运行这些循环。你有一个 run 函数，它创建一个 worktree，在 Docker 容器中沙箱化，然后允许你在里面运行一个提示。在那个 worktree 里，它就是一个 git 分支，你有代码，稍后可以合并。

如果我打开——有一些非常不错的查看方式，它基本上允许你运行这种自动化循环，并且允许你在多个代理之间简单地进行并行化。我进入 sand castle 文件，进入 main.ts，我们来看一下。这有点像之前我给你看的 Ralph 循环的版本。这里我们从顺序变成了并行。

我们首先有一个 planner，它有一个计划提示，查看 backlog 并选择一定数量的 issue 并行处理。记得我之前展示的看板中所有的阻塞关系吗？它算出所有的阶段。所以它会说——你可以忽略所有胶水代码。这基本上就是一组 issue——GitHub issues，有标题和分支让你工作。然后对于每个 issue，我们创建一个沙箱，然后在那个沙箱中运行实现，传入 issue 编号、issue 标题和分支。这就是我们刚才运行的循环。

然后如果它创建了一些提交，我们就审查这些提交。这基本上就是循环。我们对这些提交做什么？我们把它们传给一个合并代理，它接受一个合并提示，接受创建的分支，接受 issue，然后合并它们。如果合并有任何问题——类型、测试之类——它会解决。

这已经成为我在大多数项目上的工作流。它非常非常有效。嗯，是的，我建议你去看看 Sand Castle 了解更多。然后正确回答你的问题：在审查者中，我会推送编码标准；在实现中，我会允许拉取。我实际上用 Sonnet 实现，用 Opus 审查，因为我认为审查需要更多的智慧。
