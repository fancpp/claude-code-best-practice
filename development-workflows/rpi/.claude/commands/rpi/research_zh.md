## User Input

```text
$ARGUMENTS
```

你**必须**解析用户输入以提取功能标识符（`rpi/` 中的文件夹名称）。

**期望输入格式**：`rpi/{feature-slug}/REQUEST.md`

## Purpose

该命令在规划阶段开始之前对功能请求执行全面的研究和分析。它作为一个关键的 GO/NO-GO 关口，用于判断一个功能创意是否应进入详细规划阶段。

**关键目标**：
- 评估产品市场契合度和用户价值
- 评估技术可行性和复杂度
- 识别风险和潜在障碍
- 确定正确的方法（自建、购买、合作或拒绝）
- 给出明确的 go/no-go 推荐及理由

**前置条件**：
- 功能文件夹存在于 `rpi/{feature-slug}/`
- 功能请求文件存在于 `rpi/{feature-slug}/REQUEST.md`

**输出位置**：`rpi/{feature-slug}/research/RESEARCH.md`

**这是 RPI 工作流的第 2 步**（在初始功能描述 Step 1 之后）。

## Outline

1. **加载上下文**：从 `rpi/{feature-slug}/` 读取功能描述和项目章程（如果存在）
2. **解析功能请求**：使用 requirement-parser 代理提取结构化需求
3. **执行多阶段研究**：
   - 阶段 1：解析功能请求（requirement-parser 代理）
   - 阶段 2：产品分析与章程对齐（product-manager 代理）
   - 阶段 2.5：技术探索（Explore 代理）- **关键：深度代码探索**
   - 阶段 3：技术可行性评估（senior-software-engineer 代理）
   - 阶段 4：战略评估（technical-cto-advisor 代理）
   - 阶段 5：生成研究报告（documentation-analyst-writer 代理）
4. **综合推荐**：将所有分析合并为清晰的 go/no-go 推荐
5. **验证输出**：对照质量关卡检查
6. **报告完成**：提供推荐、后续步骤和报告位置

## Phases

### Phase 0: 加载上下文

**前置条件**：已提供功能标识符，`rpi/{feature-slug}/REQUEST.md` 存在

**流程**：
1. **读取功能描述**：
   - 读取 `rpi/{feature-slug}/REQUEST.md`（必需）
   - 从 REQUEST.md 中提取功能需求和目标

2. **检查项目章程**（可选）：
   - 在仓库中查找章程或原则文档
   - 常见位置：`constitution.md`、`PRINCIPLES.md`、`.project/constitution.md`
   - 如果找到，提取核心原则、约束和目标

3. **创建研究上下文**：
   - 综合为供代理使用的简洁摘要
   - 识别关键对齐标准

**输出**：
- 功能描述摘要
- 章程原则（如果找到）
- 评估对齐标准

**验证**：
- [ ] 功能文件夹存在于 `rpi/{feature-slug}/`
- [ ] 功能描述已提取
- [ ] 章程已检查并加载（如果存在）

---

### Phase 1: 解析功能请求

**前置条件**：Phase 0 完成

**代理**：requirement-parser（规划领域）

**流程**：
1. **使用功能描述启动 requirement-parser 代理**
2. **代理提取**：
   - 功能名称和类型
   - 目标组件
   - 目标和目的
   - 功能性和非功能性需求
   - 约束和假设
   - 复杂度估算
   - 澄清性问题（如有）

3. **审查解析结果**：
   - 如果存在澄清性问题，**停止并向用户询问**后再继续

**输出**：
- 结构化需求文档
- 功能元数据（名称、类型、组件、复杂度）
- 澄清性问题（如有）

---

### Phase 2: 产品分析与章程对齐

**前置条件**：Phase 1 完成，需求明确

**代理**：product-manager

**流程**：
1. **启动 product-manager 代理**，提供：
   - 来自 Phase 1 的解析后需求
   - 来自 Phase 0 的章程上下文

2. **代理分析**：
   - **用户价值**：谁受益？影响多大？
   - **市场契合度**：是否符合市场需求？
   - **产品愿景**：是否符合产品战略？
   - **章程对齐**：是否符合项目原则？
   - **约束检查**：是否违反任何章程约束？

3. **代理提供**：
   - 产品可行性评分（高/中/低）
   - 用户价值评估
   - 战略对齐评估
   - 优先级建议
   - 产品担忧或危险信号

**输出**：
- 产品可行性评估
- 用户价值分析
- 战略对齐评分
- 章程对齐摘要（如适用）

---

### Phase 2.5: 技术探索（代码探索）

**前置条件**：Phases 1-2 完成，产品可行性已确定

**代理**：Explore（通过 Task 工具，subagent_type="Explore"）

**目的**：**关键阶段** - 在做出技术可行性评估之前，深入分析现有代码库。

**流程**：
1. **启动 Explore 代理**，指定目标组件
2. **代理调查**：
   - **现有实现**：类似功能已有哪些代码？
   - **集成点**：此功能会触及哪些系统/模块？
   - **当前架构**：当前系统如何构建？
   - **数据模型**：存在哪些数据库 schema 或数据结构？
   - **依赖项**：已集成了哪些库和服务？
   - **现有模式**：使用了哪些编码模式和约定？

3. **代理提供**：
   - **当前状态摘要**：现阶段有什么
   - **集成分析**：提议功能将放在哪里
   - **代码冲突**：哪些会破坏或冲突
   - **可复用机会**：哪些可以重用 vs. 重写
   - **技术约束**：来自现有代码的实际约束

**输出**：
- 当前实现摘要
- 集成点映射
- 已识别的代码冲突
- 已识别可重用组件
- 来自代码的技术约束

**关键**：此阶段确保 Phase 3 基于**实际代码现实**，而非假设。

---

### Phase 3: 技术可行性评估

**前置条件**：Phases 1-2.5 完成，代码已探索

**代理**：senior-software-engineer

**流程**：
1. **启动 senior-software-engineer 代理**，提供：
   - 来自 Phase 1 的解析后需求
   - 来自 Phase 2 的产品上下文
   - **来自 Phase 2.5 的技术探索结果**

2. **代理分析**（基于 Phase 2.5 的发现）：
   - **技术方法**：有哪些实现选项？
   - **复杂度**：构建难度有多大？
   - **依赖项**：需要哪些系统/服务？
   - **技术债务**：这会增加还是减少技术债务？
   - **风险**：有哪些技术风险？

3. **代理提供**：
   - 技术可行性评分（高/中/低）
   - 推荐方案（及备选方案）
   - 复杂度估算（简单/中等/复杂）
   - 技术风险及缓解措施

**输出**：
- 技术可行性评分
- 推荐实现方法
- 复杂度和工作量估算
- 技术风险及缓解措施

---

### Phase 4: 战略评估

**前置条件**：Phases 1-3 完成

**代理**：technical-cto-advisor

**流程**：
1. **启动 technical-cto-advisor 代理**，提供之前所有阶段输出

2. **代理综合**：
   - **总体评估**：结合产品和技术视角
   - **战略对齐**：是否符合工程原则和项目章程？
   - **风险与回报**：价值是否值得付出努力和风险？
   - **可选方案**：自建、购买、合作、推迟或拒绝？

3. **代理提供**：
   - **Go/No-Go 推荐**：明确的决策及置信度
   - **理由**：详细的推理
   - **推荐方案**：如果选择"go"，最佳前进路径是什么？
   - **条件**：有任何继续的前提条件吗？
   - **风险**：如果继续的主要风险

**输出**：
- Go/No-Go 推荐
- 战略理由
- 推荐方案
- 风险摘要

---

### Phase 5: 生成研究报告

**前置条件**：Phases 1-4 完成

**代理**：documentation-analyst-writer（通过 Task 工具）

**流程**：
1. **启动 documentation-analyst-writer 代理**，提供所有阶段输出

2. **代理生成报告**，包含以下部分：
   - **执行摘要**：一段概览及推荐
   - **功能概览**：名称、类型、组件、目标
   - **需求摘要**：关键功能性和非功能性需求
   - **产品分析**：用户价值、市场契合度、战略对齐
   - **技术探索**：当前状态、集成点、代码约束
   - **技术分析**：可行性、方法、复杂度、风险
   - **战略推荐**：Go/no-go 及详细理由
   - **后续步骤**：基于推荐的操作建议

3. **代理创建 markdown 文件**：`rpi/{feature-slug}/research/RESEARCH.md`

**输出**：
- 完整研究报告保存至 `rpi/{feature-slug}/research/RESEARCH.md`

### 后续步骤

基于 **[GO/NO-GO]** 推荐：

**如果是 GO**：
1. 审查研究报告：`rpi/{feature-slug}/research/RESEARCH.md`
2. 继续规划：`/rpi:plan "{feature-slug}"`

**如果是 CONDITIONAL GO**：
1. 审查报告中的条件
2. 在继续前满足条件
3. 如有需要重新运行研究

**如果是 DEFER**：
1. 审查报告中的时间建议
2. 在时机适当时重新审视

**如果是 NO-GO**：
1. 审查报告中的理由
2. 考虑提到的替代方案
3. 存档以备将来参考

## 错误处理

**如果 REQUEST.md 不存在**：
- 操作：停止并通知用户
- 消息："功能请求文件 `rpi/{feature-slug}/REQUEST.md` 未找到。请先创建功能文件夹和 REQUEST.md（步骤 1：在规划模式中描述）。"

**如果功能描述过于模糊**：
- 操作：requirement-parser 将识别澄清性问题
- 消息："需要更多信息。请回答："
- 下一步：等待回答，然后继续

**如果代理失败或超时**：
- 操作：重试一次
- 下一步：如果重试失败，询问用户是否要以不完整的研究继续

## 备注

- **何时使用**：在步骤 1（描述）创建了功能文件夹之后
- **关键关口**：这可防止在不可行的功能上浪费精力
- **属于 RPI 工作流**：第 2 步（共 4 步）（描述 → 研究 → 规划 → 实施）
