# 工作流变更日志 — 设置报告

你是 claude-code-best-practice 项目的协调员。你的工作是并行启动两个研究代理，等待它们的结果，合并发现，并提交关于**设置参考**报告（`best-practice/claude-settings.md`）中差异的统一报告。

**需要检查的版本：** `$ARGUMENTS`（如果为空或不是数字，默认值：10）

这是一个**先读后报**的工作流。启动代理，合并结果，生成报告。仅在用户批准后采取行动。

---

## 阶段 0：并行启动两个代理

**立即**使用 Task 工具**在同一条消息中**生成两个代理（并行启动）：

### 代理 1：workflow-claude-settings-agent

使用 `subagent_type： "workflow-claude-settings-agent"` 生成。给它以下提示：

> 研究 claude-code-best-practice 项目的设置报告差异。检查最近 $ARGUMENTS 个版本（默认值：10）。
>
> 获取以下 3 个外部来源：
> 1. 设置文档：https：//code.claude.com/docs/en/settings
> 2. CLI 参考：https：//code.claude.com/docs/en/cli-reference
> 3. 变更日志：https：//github.com/anthropics/claude-code/blob/main/CHANGELOG.md
>
> 然后读取本地报告文件（`best-practice/claude-settings.md`）和 CLAUDE.md 文件。分析官方文档关于设置键、权限语法、钩子事件、MCP 配置、沙箱选项、插件设置、模型别名、显示设置和环境变量的说明与我们的报告文档之间的差异。返回包含缺失设置、类型/默认值变更、新增设置、已弃用设置、权限语法变更、钩子事件变更、MCP 设置变更、沙箱设置变更、环境变量完整性、示例准确性、设置层级准确性和来源有效性的结构化发现报告。

### 代理 2：claude-code-guide

使用 `subagent_type： "claude-code-guide"` 生成。给它以下提示：

> 研究最新的 Claude Code 设置系统。我需要你找到：
> 1. 所有当前支持的 settings.json 键的完整列表，包含类型、默认值和描述
> 2. 最近 Claude Code 版本中引入的任何新设置键
> 3. 现有设置行为的变更（例如新的权限模式、新的钩子事件、新的沙箱选项）
> 4. 设置层级的变更（新的优先级级别、新的文件位置）
> 5. 权限语法的变更（新的工具模式、新的通配符行为）
> 6. 新的钩子事件或钩子配置结构的变更
> 7. MCP 服务器配置的变更（新的匹配字段、新的设置）
> 8. 沙箱设置的变更（新的网络选项、新的命令）
> 9. 插件配置的变更（新的字段、新的市场选项）
> 10. 环境变量的变更（新增变量、已弃用变量、行为变更）
> 11. 模型别名或模型配置的变更
> 12. 显示/UX 设置的变更（状态行、加载动画、进度条）
> 13. 任何设置键的弃用或移除
>
> 务必详尽 — 搜索网络、获取文档，并提供具体的版本号和详细信息。

两个代理独立运行，将各自返回发现结果。

## 阶段 0.5：读取验证检查清单

**在代理运行期间**，读取 `changelog/best-practice/claude-settings/verification-checklist.md`。此文件包含累积的验证规则 — 每个规则指定要检查的内容、检查深度以及对照哪个来源。每个规则必须在第二阶段执行。该检查清单是项目用于差异检测的回归测试套件。

## 第一阶段：读取之前的变更日志条目

**在合并发现之前**，读取文件 `changelog/best-practice/claude-settings/changelog.md` 以获取最近 25 个变更日志条目。每个条目之间用 `---` 分隔。解析这些之前条目中的优先级操作，以便与当前发现进行比较。这可以让你识别：
- **重复项** — 之前出现过且仍未解决的问题
- **新解决项** — 之前运行中的问题现已修复
- **新增项** — 在此运行中首次出现的问题

## 第二阶段：合并发现并生成报告

**等待两个代理完成。** 一旦你拥有：
- **workflow-claude-settings-agent 发现** — 包含本地文件读取、外部文档获取和差异检测的详细报告分析
- **claude-code-guide 发现** — 关于最新 Claude Code 设置功能和变更的独立研究

交叉引用两者。专用代理提供报告特定的差异分析，而 claude-code-guide 代理可能揭示其遗漏的内容（例如非常近期的变更、未记录的功能或来自网络搜索的上下文）。标记两者之间的任何矛盾供用户解决。

**执行验证检查清单：** 对于 `changelog/best-practice/claude-settings/verification-checklist.md` 中的每条规则，使用代理发现作为源数据，按指定深度执行检查。在报告中包含一个**验证日志**部分，显示每条规则的结果：

```
验证日志：
规则 # | 类别           | 深度         | 结果   | 备注
1      | 设置键         | 字段级       | 通过   | 所有键匹配
2      | 权限语法       | 内容匹配     | 失败   | 新增工具模式
...
```

**必要时更新检查清单：** 如果发现揭示了一种现有检查清单规则未覆盖（或覆盖深度不足）的新差异类型，则向 `changelog/best-practice/claude-settings/verification-checklist.md` 追加一条新规则。规则必须包含：类别、检查内容、深度级别、对照来源、添加日期以及来源（什么错误触发了此规则）。不要为不会重复的一次性问题添加规则。

同时将当前发现与之前的变更日志条目（来自第一阶段）进行比较。对于每个优先级操作，将其标记为：
- `NEW` — 此问题首次出现
- `RECURRING` — 之前运行中出现过且仍未解决（包括首次出现的运行日期）
- `RESOLVED` — 之前运行中出现过但现已修复（包括解决日期）

生成包含以下部分的结构化报告：

1. **新的设置键** — 官方文档中有但报告中缺失的键，及引入版本
2. **变更的设置行为** — 类型、默认值或描述已变更的设置
3. **已弃用/已移除的设置** — 报告中有但官方文档中不再存在的设置
4. **权限语法变更** — 新的工具模式、通配符行为或权限模式变更
5. **MCP 设置变更** — 新的 MCP 配置键、匹配行为或服务器设置
6. **沙箱设置变更** — 新的沙箱选项、网络设置或命令排除
7. **插件设置变更** — 新的插件配置键或市场选项
8. **模型配置变更** — 新的模型别名、努力级别或模型环境变量
9. **显示和 UX 变更** — 新的状态行字段、加载动画选项或显示设置
10. **环境变量完整性** — 官方文档中有但报告中缺失的变量，或报告中不再有文档的变量
11. **设置层级准确性** — 验证优先级级别、文件位置和覆盖行为
12. **示例准确性** — 快速参考完整示例是否反映当前设置
13. **来源准确性** — 验证所有来源链接是否有效并指向正确的文档
14. **claude-code-guide 代理发现** — 来自该代理但未被专用代理捕获的独特见解。仅包含增加新信息的发现。如果两个代理之间存在矛盾，标记供用户解决。不要列出"已确认的一致意见"。

> **注意：** 与钩子相关的分析（事件、属性、匹配器、退出码、HTTP 钩子、钩子环境变量）**排除**在此工作流之外。钩子在 [claude-code-hooks](https：//github.com/shanraisshan/claude-code-hooks) 仓库中维护。

以优先级**操作项**汇总表结尾。每个项必须包含一个 `Status` 列，显示 `NEW`、`RECURRING (first seen：<date>)` 或 `RESOLVED`：

```
优先级操作：
#  | 类型           | 操作                                    | 状态
1  | 新增设置       | 将 <key> 添加到 <section> 表              | NEW
2  | 行为变更       | 更新 <key> 描述                          | NEW
3  | 已弃用设置     | 从表中移除 <key>                          | RECURRING（首次发现：2026-03-05）
4  | 权限语法       | 添加新的工具模式语法                       | NEW
5  | 环境变量       | 将 <var> 添加到环境变量表                  | NEW
7  | 示例更新       | 更新快速参考示例                           | NEW
```

同时包含一个**自上次运行以来已解决**部分，列出之前运行中不再存在的任何问题。

## 阶段 2.5：追加摘要到变更日志

**此阶段为强制执行 — 在向用户展示报告前必须执行。**

读取现有的 `changelog/best-practice/claude-settings/changelog.md` 文件，然后在末尾**追加**（不要覆盖）一个新条目。条目格式必须精确为：

```markdown
---

## [<YYYY-MM-DD HH：MM AM/PM PKT>] Claude Code v<VERSION>

| # | 优先级 | 类型 | 操作 | 状态 |
|---|--------|------|------|------|
| 1 | HIGH/MED/LOW | <type> | <action description> | <status> |
| ... | ... | ... | ... | ... |
```

**状态格式 — 必须使用以下三种格式之一：**
- `COMPLETE (reason)` — 已采取行动并成功解决
- `INVALID (reason)` — 发现不正确、不适用或有意为之
- `ON HOLD (reason)` — 行动推迟，等待外部依赖或用户决定

`(reason)` 为必填项，必须简要说明做了什么或原因。

**追加规则：**
- 始终追加 — 绝不覆盖或替换之前的条目
- 日期和时间是命令在巴基斯坦标准时间（PKT，UTC+5）执行的时间；通过运行 `TZ=Asia/Karachi date "+%Y-%m-%d %I：%M %p PKT"` 获取。版本来自代理发现
- 如果 `changelog/best-practice/claude-settings/changelog.md` 不存在或为空，先创建状态图例表（参见文件顶部），然后创建第一个条目
- 每个条目之间用 `---` 分隔
- **仅包含 HIGH、MEDIUM 或 LOW 优先级的项** — 省略 NONE 优先级的项（无需操作的事项）

## 阶段 2.6：更新上次更新徽章

**此阶段为强制执行 — 必须在阶段 2.5 之后、展示报告之前立即执行。**

更新 `best-practice/claude-settings.md` 顶部的"上次更新"徽章。运行 `TZ=Asia/Karachi date "+%b %d，%Y %-I：%M %p PKT"` 获取时间，进行 URL 编码（空格转为 `%20`，逗号转为 `%2C`），并替换徽章中的日期部分。如果 Claude Code 版本已变更，也更新徽章中的版本。

**不要将徽章更新记录为变更日志或报告中的操作项。** 徽章同步是每次运行的常规部分，而非发现项。

---

## 阶段 2.7：验证所有超链接

**此阶段为强制执行 — 必须在阶段 2.6 之后、展示报告之前立即执行。**

扫描 `best-practice/claude-settings.md` 中的每个超链接（包括 markdown `[text](url)` 和内联 URL）。对于每个链接：

1. **本地文件链接**（相对路径）：使用 Read 工具验证文件在解析路径处是否存在。标记任何损坏的链接。
2. **外部 URL**（例如 `https：//code.claude.com/docs/en/settings`）：使用 WebFetch 获取每个 URL 并验证其返回有效页面（不是 404 或重定向到错误页面）。标记任何失效或已移动的链接。
3. **锚点链接**（例如 `#section-name`）：验证目标标题在同一文件中存在。

在报告中包含一个**超链接验证日志**：

```
超链接验证日志：
#  | 类型     | 链接                                         | 状态   | 备注
1  | 本地     | ../                                           | 正常   |
2  | 外部     | https：//code.claude.com/docs/en/settings      | 正常   |
3  | 外部     | https：//www.schemastore.org/claude-code-settings.json | 损坏 | 404
...
```

**如果有任何链接损坏**，将其作为 HIGH 优先级操作项添加到报告中。损坏的链接降低了报告的实用性，必须在任何其他变更之前修复。

## 第三阶段：提供采取行动选项

在展示报告后（并确认变更日志和徽章都已更新），询问用户：

1. **执行所有操作** — 处理所有事项（添加缺失设置、更新描述、修复示例）
2. **执行特定操作** — 用户选择要执行的编号
3. **仅保存报告** — 不做任何变更

执行时：
- **新增设置**：以正确的类型、默认值和描述添加到适当的章节表中
- **行为变更**：更新表中设置的描述或默认值
- **已弃用设置**：在移除前与用户确认
- **权限语法变更**：使用新模式更新权限语法表
- **MCP 设置变更**：更新 MCP 设置部分
- **沙箱设置变更**：更新沙箱设置部分
- **插件设置变更**：更新插件设置部分
- **模型变更**：更新模型配置部分
- **显示变更**：更新显示和 UX 部分
- **环境变量变更**：在环境变量部分添加/更新/移除变量
- **设置层级变更**：更新设置层级表
- **示例更新**：更新快速参考完整示例以反映当前设置
- **损坏的链接**：修复或替换损坏的 URL
- 在所有操作之后，重新运行验证以确认一致性

## 关键规则

1. **在单条消息中并行启动两个代理** — 绝不顺序执行
2. **等待两个代理**完成后再生成报告
3. **绝不猜测**版本或日期 — 使用来自代理的数据
4. **新的设置键为高优先级** — 它们需要表和示例更新
5. **交叉引用设置计数** — 每个表中的设置数必须与官方文档一致
6. **不要自动执行** — 始终先展示报告
7. **始终追加到变更日志** — 阶段 2.5 是强制执行的。绝不跳过。绝不覆盖之前的条目。
8. **与之前的运行比较** — 从变更日志中读取最近 25 个条目，并将每个操作项标记为 NEW、RECURRING 或 RESOLVED。
9. **始终执行验证检查清单** — 读取 verification-checklist.md 并执行每条规则。在报告中包含验证日志。发现新类型差异时追加新规则。
10. **检查清单规则仅可追加** — 绝不移除或削弱现有规则。仅添加新规则或升级深度级别。
11. **始终更新上次更新徽章** — 阶段 2.6 是强制执行的。绝不跳过。
12. **始终验证所有超链接** — 阶段 2.7 是强制执行的。绝不跳过。损坏的链接为 HIGH 优先级。
13. **环境变量分布在两个文件中** — `claude-settings.md` 拥有 `env` 可配置的变量；`claude-cli-startup-flags.md` 拥有仅启动时变量。如果变量属于 CLI 文件，不要标记为缺失。交叉引用 `best-practice/claude-cli-startup-flags.md` 以验证所有权边界。
14. **验证设置层级** — 5 级覆盖链加上托管策略层必须与官方文档完全一致。
