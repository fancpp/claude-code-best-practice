## 背景

有了 1M token 的上下文窗口，Claude Code 可以更可靠地处理更长的任务 — 但如果你不注意管理会话，它也打开了上下文污染的大门。会话管理比以往任何时候都更重要：何时重新开始，何时压缩，何时回退，以及何时委托给子代理。

## 关于上下文、压缩与上下文腐化的快速入门

上下文窗口是模型在生成下一个响应时能够同时"看到"的所有内容。它包括你的系统提示、对话历史、每个工具调用及其输出，以及每个已读取的文件。Claude Code 拥有**一百万个 token** 的上下文窗口。

不幸的是，使用上下文有一个微小的代价 — **上下文腐化**。随着上下文的增长，模型性能会下降，因为注意力分布在更多的 token 上，旧的、不相关的内容开始干扰当前任务。对于 1M 上下文模型，一定程度的上下文腐化大约发生在 **~300-400k token** 左右，但这高度依赖于任务 — 并非硬性规则。

上下文窗口是一个硬性截断。当你接近末尾时，你需要总结任务并在新的上下文窗口中继续 — 这就是**压缩**。你也可以自己触发压缩。

## 每一轮都是一个分支点

在 Claude 完成一轮后，你有大量选项来决定下一步做什么：

- **继续** — 在同一个会话中发送另一条消息
- **/rewind (esc esc)** — 跳回到之前的消息，从那里重新尝试
- **/clear** — 开始一个新会话，通常用一个你从刚刚学到的东西中提炼出的简报
- **压缩** — 总结到目前为止的会话，在总结的基础上继续前进
- **子代理** — 将下一块工作委托给一个具有自己干净上下文的代理，只将结果拉回来

虽然最自然的做法是继续，但其他四个选项的存在是为了帮助你管理上下文。

## 何时开始新会话

新的 1M 上下文窗口意味着你现在可以更可靠地完成更长的任务 — 例如，从头构建一个全栈应用。但仅仅因为你的模型还没有耗尽上下文，并不意味着你不应该开始一个新的会话。

**经验法则：当你开始一个新任务时，你也应该开始一个新会话。**

灰色地带是，你可能想要执行一些相关的任务，其中部分上下文仍然必要，但并非全部。例如，为你刚刚实现的功能编写文档。虽然你可以开始一个新会话，但 Claude 将不得不重新读取文件，这会更慢且更昂贵。由于文档可能不是一个对智能高度敏感的任务，额外的上下文可能值得效率的提升。

## 回退而非纠正

如果 Thariq 要选择一个标志着良好上下文管理的习惯，那就是**回退**。

在 Claude Code 中，双击 Esc（或运行 `/rewind`）可以让你跳回到之前的任何消息并从那里重新提示。该点之后的消息会从上下文中删除。

**纠正**（在一个失败的尝试 A 之后说"不，试试 B"）会将失败的尝试保留在上下文中：
> 上下文 = 读取 + 2 次失败的尝试 + 2 次纠正 + 修复

**回退**（回到失败的尝试之前，用你学到的东西重新提示）则更干净：
> 上下文 = 读取 + 一次有依据的提示 + 修复

回退通常是更好的方法。例如，Claude 读取了五个文件，尝试了一种方法，但没有成功。你的直觉可能是输入"那不行，试试 X 代替。"但更好的做法是回退到文件读取之后，用你学到的知识重新提示："不要使用方法 A，foo 模块没有暴露那个——直接使用 B。"

你也可以使用**"从这里的总结"**让 Claude 总结其学习并创建交接信息，就像 Claude 的某个版本从未来的自己（尝试过某事但没有成功）那里收到消息一样。

## 压缩 vs. 新会话

一旦会话变长，你有两种方式减轻负担：`/compact` 或 `/clear`（重新开始）。它们感觉相似，但行为截然不同。

**压缩**让模型总结到目前为止的对话，然后用该总结替换历史记录。它是有损的——你相信 Claude 能决定什么重要，但你不需要自己写任何东西。Claude 可能更彻底地包含重要的学习或文件。你也可以通过传递指令来引导它（`/compact focus on the auth refactor, drop the test debugging`）。

- **任务进行中时**，保持势头——细节可以模糊
- 低成本，继续前进

**新会话 + 简报**（`/clear`）意味着*你*写下重要的事情（"我们正在重构 auth 中间件，约束条件是 X，重要的文件是 A 和 B，我们已经排除了方法 Y"）并重新开始。这更费功夫，但产生的上下文是*你*认为相关的内容。

- **高风险的下一步**——在 100K 的探索中发现了一个事实
- 更多工作量，更精确

## 什么导致了不好的压缩？

如果你运行了很多长时间的会话，你可能注意到有时压缩效果特别差。当模型无法预测你的工作方向时，就会发生糟糕的压缩。

例如，自动压缩在一次长时间的调试会话后触发，并总结了调查过程。你的下一条消息是"现在修复我们在 bar.ts 中看到的那个其他警告。"但由于会话专注于调试，那个其他警告可能已经从摘要中丢失了。

这尤其困难，因为由于上下文腐化，模型在压缩时处于最不智能的状态。拥有一百万上下文，你有更多时间主动使用 `/compact` 并附带你想要做的事情的描述。

## 子代理与新的上下文窗口

子代理是上下文管理的一种形式，当你预先知道一块工作会产生大量你不再需要的中间输出时，这非常有用。

当 Claude 通过 Agent 工具生成子代理时，该子代理会获得自己全新的上下文窗口。它可以做它需要的所有工作，然后综合其结果，只有最终的摘要返回给父代理。

思维测试：**我还会需要这个工具的输出，还是只需要结论？**

探索噪音在子代理退出时被垃圾回收——20 次文件读取、12 次 grep、3 个死胡同——只有最终报告返回给父上下文。

虽然 Claude Code 会自动调用子代理，但你可能希望明确告诉它这样做。例如：

- "启动一个子代理，根据以下规范文件验证此工作的结果"
- "派一个子代理去阅读其他代码库，总结它是如何实现 auth 流程的，然后你自己以同样的方式实现它"
- "派一个子代理根据我的 git 变更为此功能编写文档"

## 总结

当 Claude 完成了一轮，而你要发送新消息时，你面临一个决策点。随着时间的推移，Claude 会自己处理这个，但现在这是你可以引导 Claude 输出的方式之一。

| 情况 | 采用方式 | 原因 |
|-----------|-----------|-----|
| 同一任务，上下文仍然相关 | **继续** | 窗口中的所有内容仍然重要——不要为重建它付出代价 |
| Claude 走错了路 | **回退**（双击 Esc） | 保留有用的文件读取，丢弃失败的尝试，用你学到的重新提示 |
| 任务进行中但会话因过时的调试/探索而臃肿 | **/compact \<提示\>** | 低努力；Claude 决定什么重要。如有需要，用提示引导它 |
| 开始一个真正的新任务 | **/clear** | 零腐化；你精确控制传递什么 |
| 下一步将产生大量你只需要结论的输出 | **子代理** | 中间工具噪音留在子上下文中；只有结果返回 |
