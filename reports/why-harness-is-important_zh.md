# 为什么 Harness 很重要

为什么 Claude Code 的功能不是"伪装的提示"——以及为什么 harness 才是真正将玩具输出与生产级工程工作区分开的关键。

## 执行摘要

有经验的 Claude Code 用户中一个常见的简化论是：*"技能、命令、子代理、钩子——它们最终都会变成给模型的提示，所以一个强大的提示本身就足够了。"*

在模型最终推理调用的层面，这在技术上是正确的。模型只能看到 token。

但在其他每一个层面——在真正的软件工程发生的层面——**这个简化论就不成立了。** Harness 不是一个提示传递系统。它是一个**提示构建系统、一个确定性执行系统和一个上下文架构系统**——而这些能力是无法被更强大的措辞所替代的。

本报告解释了简化论在什么地方是正确的，在什么地方失效，以及为什么混淆"模型看到什么"和"系统做什么"会让从业者远离那些赋予 Claude Code 实际杠杆作用的功能。

---

## 听起来正确的简化论

对于一个**一次性原子任务**——"给我写一个递归斐波那契函数"——harness 对输出质量没有任何贡献。无论通过技能、命令还是原始提示到达模型，将相同的 token 交给相同的模型，你都会得到相同的输出分布。

在这个狭窄的领域中，简化论成立：

> 输出质量 ≈ 提示质量

在这个领域中，Claude Code 比普通聊天机器人提供的价值很少。这也是简化论隐含假设的领域——恰恰是真正的工程工作不在的领域。

## 简化论在什么地方失效

Harness 的十种架构能力在提示无法触及的层面上运作。

| # | 能力 | 作用 | 为什么提示无法复制 |
|---|------------|--------------|-------------------------------|
| 1 | **上下文隔离** | 子代理在独立的上下文窗口中运行 | 一个提示填充一个窗口。N 个并行子代理提供约 N 倍的有效上下文。 |
| 2 | **Harness 强制工具限制** | `allowed-tools` / `disallowedTools` 在模型使用前阻止工具 | 提示指令是建议性的；模型可以忽略它们。拒绝规则不能被忽略。 |
| 3 | **延迟加载的规则和内存** | `paths:` frontmatter 和后代 `CLAUDE.md` 文件仅在 Claude 触及匹配路径时加载 | 提示是静态的——它无法根据运行时正在读取哪些文件进行条件加载。 |
| 4 | **钩子：确定性代码执行** | Shell 命令在生命周期事件中运行（PreToolUse、PostToolUse、Stop 等），并且可以**阻止**工具调用 | 提示无法拦截自己的工具调用。即使模型不"想要"它们执行，钩子也会执行。 |
| 5 | **模型路由** | `model: haiku` 或 `model: opus` 将调用路由到不同的模型端点 | 提示中没有 token 可以改变哪个模型来回答。 |
| 6 | **并行性** | 多个子代理并发执行 | 提示是顺序的。Harness 调度并收集并行进程的结果。 |
| 7 | **跨会话持久性** | 内存系统和设置层级跨会话持久化 | 提示在会话结束时消亡。 |
| 8 | **模块化系统提示** | CLI 根据激活的功能有条件地加载 110+ 个系统提示片段 | 用户无法手动编写或替换 CLI 的内部提示片段。 |
| 9 | **技能预加载** | `skills:` 字段将技能的全部内容注入子代理的起始上下文 | 用户无法预填另一个代理的上下文——只有 harness 加载器可以。 |
| 10 | **权限分类** | `auto` 权限模式使用后台分类器预先批准或阻止工具调用 | 提示无法为自己添加执行前安全层。 |

每一行都是一个维度，"强大的措辞"绝对不是替代品。

## "提示"一词的两种用法

简化论依赖于一词多义。*提示*这个词被用来指代两种截然不同的东西：

| 含义 | 谁控制它 | 大小 |
|---------|-----------------|------|
| (a) 用户输入的内容 | 用户 | ~6–60 token |
| (b) 推理时模型看到的内容 | Harness | ~5,000–50,000+ token |

在聊天机器人中，(a) 和 (b) 是同一个东西。
在 Claude Code 中，它们截然不同。

Harness 的工作正是使 (b) 比 (a) 丰富得多：

```
用户输入："写一个递归展平函数"                      ← (a) ~6 token

推理时模型实际看到的内容：                            ← (b) ~15,000 token
  ├── CLAUDE.md（项目约定）
  ├── 匹配的 .claude/rules/*.md（通过 paths: frontmatter 加载）
  ├── 模块化系统提示片段
  ├── 工具定义
  ├── 环境上下文（cwd、git 状态、平台）
  ├── 先前的轮次历史
  ├── 模型通过 Read/Grep 工具读取的文件
  └── 用户的 6 token 请求
```

**输出质量是 (b) 的函数，而不是 (a)。** Harness 构建了 (b)。仅靠"强大的提示"无法重现 (b)，因为其中大部分不是用户编写的。

## 即使对于输出质量，Harness 也在发挥作用

考虑相同的提示——"写一个递归展平函数"——在三个环境中：

| 环境 | 模型看到的内容 | 典型结果 |
|-------------|---------------------|----------------|
| 聊天机器人，无工具 | 句子 | 教科书式递归，通用风格 |
| Claude Code，无读取 | 句子 + CLAUDE.md | 匹配声明的项目约定 |
| Claude Code，代理循环 | 句子 + CLAUDE.md + 读取相邻文件 + 运行测试 | 匹配实际代码库模式，通过测试，处理现有代码处理的边界情况 |

相同的模型。相同的用户提示。**三种不同的输出质量。** 区别在于 harness——具体来说，是它组装的有效上下文和它启用的迭代循环。

对于非平凡任务，输出质量是以下因素的函数：

```
输出质量 = f(有效上下文, 模型能力, 迭代循环)
```

用户控制*有效上下文*的一小部分（他们输入的提示）。Harness 控制其余部分——以及完整的迭代循环。

## 简化论做对了什么（以及做错了什么）

| 说法 | 结论 |
|-------|---------|
| "在推理时，模型只能看到 token。" | ✅ 正确 |
| "技能、命令和子代理提示都为某个上下文贡献了 token。" | ✅ 正确 |
| "对于真空中的原子任务，提示质量主导输出质量。" | ✅ 正确 |
| "因此，一个强大的提示等同于使用各种功能。" | ❌ 错误 |
| "因此，harness 对输出质量无关紧要。" | ❌ 在真实工程任务上是错误的 |

前三个陈述是准确的观察。跳到第四个是推理失败的地方：它混淆了模型与其包裹它的系统，并混淆了原子任务与真实工程工作。

## 正确的思维模型

> **提示控制模型被要求做什么。**
> **Harness 控制在模型无法触及的层面上系统做什么**——在 token 到达之前、在 token 产生之后、跨会话、跨上下文和跨进程。

功能不是提示加上额外步骤。它们是 **harness 级别的原语**——确定性执行、上下文架构和基础设施路由——在模型无法发声的层面上运作。

一个有用的类比：

| 层面 | 聊天机器人 | Claude Code |
|-------|---------|-------------|
| 配方 | 用户的消息 | 用户的消息 + harness 组装的上下文 |
| 厨房 | 无——只有一个学生 | 工具、钩子、内存、并行工作者、生命周期事件 |

你可以写出世界上最好的配方。没有厨房，你无法大规模烹饪。

---

## 对实践者的启示

1. **对于原子问题，提示质量几乎就是一切。** Harness 无关紧要。如果那是你需要的全部，那就用聊天机器人。
2. **对于真实的代码库工作，harness 在默默承担繁重的工作。** 推理时的有效提示主要是 harness 构建的，而非用户输入的。
3. **使用功能来做提示根本无法做到的事情：** 确定性（钩子）、隔离（子代理）、延迟加载（带有 `paths:` 的规则）、持久性（内存）、路由（每个代理的 `model:`）和并行性。
4. **强大的提示是必要但不充分的。** 功能提供了提示无法实现的确定性、隔离和组合。两者是互补的，而非替代关系。
