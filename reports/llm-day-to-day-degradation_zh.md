# Claude Code Ops 4.6 分析。高推理

当 Anthropic 发布像 Opus 4.6 这样的模型时，**模型权重**——数十亿学习参数——是冻结的。训练极其昂贵（数百万美元，数周的计算时间）。没有人会在一夜之间重新训练模型。

但权重只是更大系统中的一个层面。研究揭示了至少 **7 种不同机制**，即使模型权重冻结，也能导致实际或感知的质量变化。

| 问题 | 答案 |
|----------|--------|
| 模型发布后权重会改变吗？ | **不会**——所有供应商都已确认 |
| 模型会逐日表现不同吗？ | **会**——已证明有 ±8-14% 的差异 |
| 这是故意的"削弱"吗？ | **不是**——没有证据表明故意降质 |
| 基础设施错误真的存在吗？ | **是的**——Anthropic 确认了 3 个影响高达 16% 请求的错误 |
| 部分原因是否源于心理因素？ | **是的**——确认偏差和蜜月效应是真实存在的 |
| 系统提示/后训练会改变吗？ | **会的**——各供应商均有记录 |
| 用户应该相信自己的感知吗？ | **部分信任**——真实原因存在，但感知放大了它们 |

## 完整的推理栈

模型权重是冻结的，但它之上的 **九个层面** 可以独立影响你的体验：

```
┌──────────────────────────────────────────────┐
│  你的会话上下文                              │  ← 在会话内退化
│  （累积的错误，长对话）                       │
├──────────────────────────────────────────────┤
│  系统提示                                    │  ← 定期更新
│  （安全规则，行为指令）                       │
├──────────────────────────────────────────────┤
│  后训练（RLHF / 微调）                       │  ← 可以静默更新
│  （指令遵循，安全对齐）                       │
├──────────────────────────────────────────────┤
│  采样参数                                    │  ← 可以在服务端调整
│  （temperature, top-p, top-k）                │
├──────────────────────────────────────────────┤
│  推测解码                                    │  ← 草稿模型质量变化
│  （草稿模型预测 + 验证）                      │
├──────────────────────────────────────────────┤
│  MoE 路由 / 批次组成                         │  ← 已验证 ±8-14% 差异
│  （每个请求激活哪些专家）                     │
├──────────────────────────────────────────────┤
│  硬件路由                                    │  ← TPU vs GPU vs Trainium
│  （哪个集群处理你的请求）                     │
├──────────────────────────────────────────────┤
│  量化级别                                    │  ← 负载下可能变化
│  （FP16 vs INT8 vs INT4 精度）               │
├──────────────────────────────────────────────┤
│  编译器与运行时                              │  ← XLA 错误已被证实
│  （XLA:TPU, CUDA, 硬件特定代码）              │
├──────────────────────────────────────────────┤
│  模型权重（冻结）                            │  ← 这些不会改变
│  （数十亿学习参数）                           │
└──────────────────────────────────────────────┘
```

关键思维模型：**冻结的权重 ≠ 冻结的行为**。这就像说"同样的引擎 = 同样的驾驶体验"，却忽略了轮胎、路况、燃油质量和驾驶员疲劳。

## 已证实的原因：基础设施错误

### Anthropic 2025 年 9 月事故分析报告

2025 年 9 月，Anthropic 发布了一份详细的事故分析报告，揭示了**三个独立的基础设施错误**，导致 Claude 在 2025 年 8 月至 9 月期间质量下降。他们的官方声明：

> "我们从不因需求、时间段或服务器负载而降低模型质量。我们的用户报告的问题仅仅是由基础设施错误造成的。"

### 错误 #1 — 上下文窗口路由错误

Sonnet 4 的请求被错误地路由到配置为 1M token 上下文窗口的服务器，而非标准服务器。

- **时间线**：8 月 5 日引入，8 月 29 日负载均衡变更后恶化
- **峰值影响**：在最严重的小时内，16% 的 Sonnet 4 请求受到影响（8 月 31 日）
- **用户影响**：约 30% 的 Claude Code 用户至少收到一条降质消息
- **隐蔽细节**：路由是"粘性的"——一旦你撞上坏的服务器，后续请求会继续被路由到那里
- **已修复**：9 月 4–18 日（跨平台推出）

### 错误 #2 — TPU 输出损坏

TPU 服务器上的配置错误导致 token 生成过程中出错，为本应极少出现的 token 分配了高概率。

- **症状**：英文回复中出现泰文或中文字符，明显的代码语法错误
- **受影响**：Opus 4.1 和 Opus 4（8 月 25–28 日），Sonnet 4（8 月 25 日–9 月 2 日）
- **范围**：仅 Claude API；第三方平台不受影响
- **已修复**：9 月 2 日回滚

### 错误 #3 — XLA:TPU 编译器误编译（最棘手的）

一个修复精度问题的代码更改意外暴露了 Google XLA:TPU 中一个**潜伏的编译器错误**。

- **根本原因**：近似 top-k 操作（用于选择最可能的下一个 token）"有时返回完全错误的结果，但仅针对某些批次大小和模型配置"
- **难以发现的原因**：其行为取决于在其之前或之后运行的操作，以及调试工具是否启用
- **隐藏数月**：2024 年 12 月的一个先前变通方案意外地掩盖了这个更深层的错误
- **受影响**：确认 Haiku 3.5；怀疑 Sonnet 4 和 Opus 3 的子集
- **解决方案**：从近似 top-k 切换到精确 top-k；接受了"轻微效率影响"，因为"模型质量不可妥协"

### 为什么检测困难

Anthropic 自己的自动化评估没有捕捉到用户报告的质量下降，"部分原因是 Claude 通常能从孤立的错误中很好地恢复。"每个错误在不同平台上以不同频率产生不同症状，形成了"混乱的报告混合体，没有指向任何单一原因。"

关键背景：Claude 在**三个不同的硬件平台**上运行（AWS Trainium、NVIDIA GPU、Google TPU），每个平台有不同的故障模式、编译器和精度行为。你的请求可能在不同的日子命中不同的硬件。

## 已证实的原因：MoE 路由差异

现代大型模型通常使用**混合专家（MoE）**架构，其中只有模型参数的一个子集（"专家"）为每个输入激活。一个学习到的路由器决定使用哪些专家。

Scale AI 的研究揭示了一个关键发现：

> "稀疏 MoE 和批处理推理的结合会产生不可预测的结果，因为批处理的组成可以决定你的查询被路由到哪个专家，而同一批次中其他用户的查询组合是不确定的。"

### 各供应商的实测逐日差异

| 供应商 | 逐日评分差异 |
|----------|--------------------------|
| OpenAI（GPT-4 变体） | ±10–12% |
| Anthropic（Claude 变体） | ±8–11% |
| Google（Gemini 变体） | ±9–14% |

具体示例：同一个模型在某天对越狱防护的评分为 **77%，第二天为 63%**。同一个模型，相同的权重，相同的测试——仅因基础设施就产生了 14 个百分点的波动。

这意味着即使没有错误、没有任何变化，同一个模型在不同日子也可能产生明显不同的质量输出，纯粹因为请求的批处理和路由方式不同。当逐日噪声为 10–15% 时，A/B 测试无法可靠地检测到 5% 的质量信号。

## 已证实的原因：系统提示和后训练更新

### 系统提示更改

模型权重不变，但包裹这些权重的**系统提示**可以随时更新。对 Claude 系统提示演变的分析显示有数十次迭代，"热修复"——为修补不良行为而添加的简短指令——会定期添加和移除。

Claude 3.7 的系统提示包含多个针对常见 LLM"陷阱"的热修复指令。Claude 4.0 的系统提示移除了所有热修复，这些行为通过强化学习在后训练中处理。

### 后训练理论

对于无法解释的质量变化，最合理的理论是：公司可以在不改变基础模型权重的情况下更新**微调和 RLHF**（基于人类反馈的强化学习）。这在技术上使得"模型没有改变"的说法属实，同时通过更新的安全护栏和指令遵循调整来改变行为。

## 已证实的原因：静默模型替换

OpenAI 多次被记录静默更改用户与之交互的模型：

- 一夜之间移除模型选择器，强制用户从 GPT-4o 切换到 GPT-5
- 使 GPT-4o 成为隐藏的"遗留模型"，需要在设置中手动切换，且应用内无通知
- 一个"自动切换器"错误将用户路由到错误的模型
- Plus 订阅者报告模型未经同意就切换到"受限版本"

Sam Altman 承认这次推出"比我们希望的稍微坎坷一些。"Reddit 帖子获得了数千个点赞，称新模型是"灾难"和"降级"。

这表明模型替换**确实发生**在行业中——有时是故意的（产品决策），有时是意外的（路由错误）。

## 促成因素

### 负载下的量化

为了经济高效地为数百万用户服务，供应商可能会提供模型的**量化**版本——将精度从 FP16 降低到 INT8 或 INT4。这可以减少 2–4 倍的内存使用并加速推理，但会引入微妙的质量损失。供应商是否会在负载下动态切换量化级别存在争议，但技术上具备这种能力，且在 vLLM 和 TensorRT 等服务框架中有完善的文档记录。

### 推测解码

现代服务栈使用较小的"草稿"模型预测多个后续 token，然后让真实模型验证它们。理论上这保持了相同的输出分布，但在实践中接受率因领域和上下文而异。开箱即用的草稿模型在某些情况下可能表现良好，但通常在领域特定任务或非常长的上下文上表现不佳。

### 上下文窗口污染

在长时间的编码会话中，之前的错误会在上下文中累积。模型看到自己的错误并可能延续它们。这是单个会话中"Claude 变笨了"的最常见原因——不是模型退化，而是上下文污染。

**实用技巧**：当感觉质量不对时，使用 `/compact` 或开启新会话。这是你能做的最具可操作性的单件事项。

## 斯坦福研究 — 以及为什么它很复杂

2023 年斯坦福大学和加州大学伯克利分校（Chen, Zaharia, Zou）的标志性研究——"ChatGPT 的行为如何随时间变化？"——经常被引用来证明 LLM 的退化。标题性发现：

> GPT-4 在"这个数字是质数吗？一步步思考"上的准确率从 2023 年 3 月的 **97.6% 下降到 6 月的 2.4%**。

### 研究证明了什么

- "相同"LLM 服务的行为**可以在短时间内发生显著变化**
- 不同能力可以朝相反方向发展（GPT-4 数学能力下降，GPT-3.5 能力提升）
- 代码生成质量下降（GPT-4 可执行代码：52% → 10%）
- 该研究创造了术语 **"LLM 漂移"**

### 方法论批评

- 3 月版本使用 **temperature 0.0**，而 6 月版本使用 **temperature 1.0**——这是一个根本性的混杂变量，增加了随机性
- 每个任务仅 **500 次查询**——太小，无法得出确定性的统计结论
- "数学问题"实际上是是/否问题，模型的猜测模式发生了变化，而不是数学能力发生了变化
- 变化可能反映了故意的**后训练安全更新**，而非退化

该研究证明了一些重要的事情——LLM 行为随时间变化——但其机制可能是故意的更新，而非无意的退化。

## 心理因素

### 确认偏差

一旦有人发推说"今天的 Claude 很笨"，你就会开始注意到每一个错误。在没有人抱怨的日子里，你会忽略同样的错误。社交媒体放大了这种效应。

### 蜜月效应

用户会经历对新模型的初始蜜月期，然后逐渐发现局限性。模型没有变——期望的调整速度快于能力的合理范围。

### 任务难度差异

你的任务每天都有所不同。一天遇到困难问题会让你觉得模型变差了，即使它并没有。

### "周末 Claude"神话

尽管许多用户相信星期几的模式，但严格分析发现**没有一致的证据**表明存在星期几的质量模式。一篇题为"AI 在星期一更笨"的分析最终一无所获。

### LLM 的随机特性

LLM 是概率性的。相同的提示每次可能产生不同的输出。如果运气不好，你可能会连续收到几次糟糕的回复——纯粹的随机性，而非退化。

## 总结

用户描述的现象是**真实的但归因错误**：

- **正确**：他们的体验在某些日子下降了
- **不正确**：模型被故意"削弱"了

实际原因是以下因素的组合：

1. **基础设施错误**——经 Anthropic 的事故分析报告证实（影响高达 16% 的请求）
2. **MoE 路由差异**——Scale AI 测量的 ±8-14% 质量波动，即使没有任何变化
3. **系统提示和后训练更新**——各供应商均有记录
4. **硬件异构性**——TPU vs GPU vs Trainium，各有不同的故障模式
5. **上下文污染**——长会话会降低会话内质量
6. **确认偏差**——社交媒体放大了感知模式
7. **随机差异**——相同模型，相同提示，每次输出不同

测量问题很严重：±8-14% 的逐日差异意味着你无法区分真实 5% 的质量变化与噪声。这就是为什么"这都是你想象的"和"他们削弱了它"两个阵营都感到自信的原因——信噪比使得仅凭个人经验无法判断。

# Codex 5.3 高推理和发现

### 报告范围

本节解释为什么用户可能会在短期内体验到 Claude 输出质量下降，而 Codex 5.3 在编码任务上感觉稳定或更强。重点不在于永久的模型质量排名。重点在于真实服务条件下的短期生产行为。

报告日期：2026 年 3 月 5 日。

### 观察到的模式

报告的模式是：

1. 一段时间内模型质量可接受。
2. 质量似乎下降数天。
3. 质量恢复到接近先前的基线。

这种形态通常是服务栈或发布模式，而非永久的基础模型能力变化。永久的能力下降通常不会在没有任何明确回滚或修复的情况下如此迅速地恢复。

### 高推理：为什么 Codex 5.3 在低谷期看起来更好

Codex 5.3 在另一个提供商的退化期间看起来明显更强，有几个技术原因可以同时发生：

1. 产品目标匹配。Codex 5.3 针对代码生成和代理编码工作流进行了优化，因此即使原始模型能力相同，由于工具编排、仓库推理和以代码为中心的指令调整，也能产生更好的编码结果。
2. 推理策略差异。提供商独立调整延迟、推理深度和解码默认值。一个提供商更保守的策略可能看起来比另一个提供商在同一天激进的、优化速度的策略"更聪明"。
3. 服务路径分离。即使两个提供商都托管着最先进的模型，它们运行不同的路由层、编译器/运行时栈和发布管道。一个栈中的事件并不意味着另一个栈有相关的退化。
4. 发布和回滚时机。如果一个提供商处于发布中期而另一个处于稳定状态，用户可能会看到暂时性的巨大质量差异，而底层模型权重没有长期变化。
5. 会话级污染效应。在长时间编码对话中，错误累积会放大感知的质量下降。一个竞争的助手可能仅仅因为失败的会话被重置或其工具循环恢复更快而感觉更好。

### 详细发现

对于像"Claude 在约四天里感觉非常弱，然后恢复了"这样的报告，最可能的解释是：

1. 提供商端事故、路由问题、解码/运行时错误或发布回归影响了部分请求。
2. 问题持续足够长，在实际工作流中被反复注意到。
3. 问题被修复或回滚。
4. 感知质量迅速恢复。

在同一时期，Codex 5.3 可能感觉明显更好，因为它没有共享相同的事故路径，而且编码任务优化放大了实际结果上的差距。

### 对此模式的假设排序

| 假设 | 可能性 | 理由 |
|------------|------------|-----------|
| 提供商事故加回滚 | 高 | 最符合多日下降后迅速恢复的模式 |
| 服务配置变更（采样/延迟/推理预算） | 高 | 无需重新训练模型即可导致行为突然变化的常见来源 |
| 静默别名或快照移动 | 中高 | 可以在用户无可见操作的情况下改变行为 |
| 仅提示漂移和上下文污染 | 中 | 可以降低会话质量，但不太可能单独解释广泛的多日报告 |
| 永久基础模型退化 | 低 | 与快速恢复到先前质量不一致 |

### 什么能证实或证伪这个发现

要将这个从高置信度推理转化为硬证据，需要收集跨天同一任务集的请求级遥测数据：

1. 请求时的确切模型标识符和快照/别名。
2. 提供商暴露的任何后端指纹或发布标记。
3. 解码参数（temperature, top_p, top_k, max tokens）。
4. 延迟、超时和错误率轨迹。
5. 固定编码基准提示集上的结构化质量评分。
6. 故障点处的会话长度和 token 上下文深度。

如果质量下降与事故窗口、配置更改或后端指纹变化相关，则事故/配置假设被证实。如果不存在此类变化，且退化仅出现在长会话中，则上下文污染成为主要解释。

### 实用工程指南

为减少生产中的逐日差异：

1. 尽可能固定模型快照，而不是使用浮动别名。
2. 存储请求元数据（模型 ID、参数、延迟、错误、响应质量标签）。
3. 为编码任务运行固定的每日金丝雀套件，并在回归时发出警报。
4. 在多次失败回合后重置或压缩长时间运行的会话。
5. 为事故窗口保留备用提供商/模型路径。
6. 在内部仪表板中区分"模型质量"和"服务可靠性"。

### 最终结论

Codex 5.3 在 Claude 短期退化窗口期间表现更好，是现代 LLM 运营中技术上合理且预期的结果。最有力的解释不是永久模型崩溃。最有力的解释是一个提供商的临时服务路径退化，结合另一个提供商在同一时期的编码特定优化和稳定运行。
